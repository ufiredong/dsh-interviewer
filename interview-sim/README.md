# 实证材料

这里不是"示例"，是**这个插件的设计依据**。面试官的每一条硬规则背后都有一场真跑过的面试，
这个目录把那些跑过的东西留下来，让结论可以被复查、被推翻。

所有脚本都打真实模型（走插件的 `/interviewer/api/chat` 路由），
候选人由脚本扮演 —— **答案刻意做好了坏的分布**：强回答、一知半解、明确不知道、
含糊其辞都有。全是好答案的话，评出来的分没有信息量，那不是在测面试官，是在演戏。

> 前提：DSH 正在运行，且插件已装。脚本打的是 `http://127.0.0.1:3080/interviewer/api/chat`。

## 行为回归（改动后必跑）

| 脚本 | 验什么 |
|---|---|
| `state-run.mjs` | **状态机版**：11 轮真实对话。判据是「没有话题超过 2 问」+ 「走过几个不同话题」 |
| `run.mjs` | **无状态版**（对照）：同一套台词，没有状态机。用来证明问题真实存在 |

两版用**完全相同**的候选人台词，所以可以直接对比。结果见
[`transcript.md`](transcript.md)（无状态）与 [`transcript-state.md`](transcript-state.md)（状态机）：

| | 无状态版 | 状态机版 |
|---|---|---|
| 单话题最多追问 | 4 轮（「多出来的 1.5 秒」反复重问） | 2 轮 |
| 走过的不同话题 | 2 个 | 6 个 |
| 收尾表现 | `max-tokens` 挂掉 | 「好，我整理一下」 |

```bash
node state-run.mjs
```

## 协议调参（当时为什么要那么设计）

这几支是"用实测定设计"，不是拍脑袋。留着是为了下次有人想改协议时，
先看见上一轮的结论是怎么来的、样本量有多大。

| 脚本 | 结论 |
|---|---|
| `probe-tokens.mjs` | **推理 token 也计入 `maxTokens`。** 带状态协议时 1600 不够、3000 还不够、5000 才稳 —— 这是"空产出自动重试"的来源 |
| `probe-protocol.mjs` | 第一轮比三种协议形式（JSON / 一行 / 一行+计划），3 样本，噪声大 |
| `probe-protocol2.mjs` | 加到 5 样本，**把上一轮的猜测推翻了**：20 次调用全成功，`max-tokens` 是模型自己的波动，不是协议贵。但暴露出真问题 —— 标记命中率只有 1/5 |
| `probe-protocol3.mjs` | 试"把协议挪到提示词最末尾"。结果反而更差（1/5 vs 中间位置的 4/5），同样是 5 样本 |

**样本量只有 5，所以结论只到「换措辞和挪位置都救不回来」这一层。**
再往下就不敢下了 —— 所以设计上直接选择了**不依赖模型配合**（乐观前进 + 点名换话题），
而不是继续调提示词。这也是这几支脚本留在仓库里的原因：
它们记录了"什么时候该停止调参、改用架构解决"。
