## 面试过程

### 话题 1：订单创建链路重构

| | |
|---|---|
| 钻到的深度 | L3（实现细节） |
| 用时 | 约 6 轮 |

**提问链**

1. 「7 次 RPC 拆完之后，这块代码具体哪几块是你亲手写的？」
2. 「7 个下游平均 120 毫秒，加起来八百多 —— 但 P99 是 2.4 秒。中间差的那 1.5 秒在哪？」
3. （连续追问 3 轮）
4. 「库存 Lua 预扣成功、异步落库失败，这笔扣减怎么办？」

**候选人的关键回答（原话）**

> 「拆 RPC 是我主导的。原来订单创建要串行调 7 个下游：风控、库存、优惠、会员、地址、
> 支付预下单、日志，每个平均 120 毫秒，加起来就 800 多毫秒。我先做了依赖分析，
> 发现 4 个可以并行、3 个能挪到异步。」

**观察**

这一段是本场最强的部分：**做了依赖分析再动手**，不是拍脑袋优化的。
"4 个并行、3 个异步、只留 2 次同步 RPC" —— 有取舍、有理由。

但面试官抓到一个真缺口：**均值 840ms 和 P99 2400ms 之间的 1.5 秒没有解释**。
这是简历里埋着的数字矛盾，候选人**连续 4 轮都没能回答**。

最后那一问（Lua 预扣成功但落库失败）也**没有答上来** —— 而这恰恰是他简历里
自己写的方案，正常应该张口就来。

### 话题 2：缓存一致性

| | |
|---|---|
| 钻到的深度 | L2（选型层就卡住） |
| 用时 | 1 轮 |

**提问**

- 「多实例部署时，本地缓存的内容不一样，会出什么问题？」

**候选人的关键回答（原话）**

> 「多实例本地缓存的一致性……这个问题当时是我们组另一个同事主做的，我了解得没那么细。
> 我知道最后是用 Redis 的 pub/sub 广播失效，但怎么保证广播不丢、重启期间怎么办，
> 我没深入看。」

**观察**

**这是本场最诚实也最加分的一句。** 边界标得很干净：知道什么、不知道什么、
连"不知道到哪一层"（广播不丢、重启期间）都说清楚了。

按 `references/04-scoring.md`，这正是「边界认知」维度 5 分的锚点描述。

但也要注意：**他简历上写着"我来设计缓存层"，而被问到一致性时却推给了同事。**
两者之间的落差面试官没有点破（按铁律也不该点破），但记录在案。

### 话题 3：JVM 调优

| | |
|---|---|
| 钻到的深度 | L2，且**没钻下去** |
| 用时 | 2 轮 |

**候选人的关键回答（原话）**

> 「JVM 这块处理过 Full GC 频繁的问题，当时加了 GC 日志分析，调过堆大小和一些参数，后来就好了。」
>
> 「具体哪个参数……我记得调过 -Xmx 和新生代比例，还有那个……CMS 还是 G1 我记不太清了，
> 是运维同事帮忙一起看的。」

**观察**

**这是本场最弱的一段，而且面试官漏掉了。**

「调过堆大小和**一些参数**」「**后来就好了**」—— 这是教科书级的含糊（铁律 3 的触发词），
按 SOP 必须立刻追问。但面试官因为还困在前面那个 1.5 秒里，
只回了一句"那 1.5 秒这个先过"就跳到下一个话题，**放掉了**。

简历上写"熟悉 JVM 调优"，实测是"参与过一次，细节记不清，是运维主导的"。

### 话题 4：分库分表复盘

| | |
|---|---|
| 钻到的深度 | L5（复盘） |
| 用时 | 1 轮 |

**候选人的关键回答（原话）**

> 「最大的坑是分库分表那次数据迁移，原计划两周，拖了一个半月。
> 问题出在我们一开始只校验主键，没校验业务字段。切流到 10% 才发现一批订单金额对不上，
> 原因是迁移脚本里 decimal 转换丢了一点精度。后来补了全字段比对，又加了灰度回滚才敢继续。
> 现在回头看，那次的问题不是技术难，**是我们把"数据一致"当成了可以抽查的东西**。」

**观察**

**本场第二强的回答。** 有具体时间（两周 → 一个半月）、有根因（decimal 精度）、
有补救（全字段比对 + 灰度回滚），而且最后自己上升到了方法论层面。

这句话说明他**把一次教训真正内化了** —— 不是"下次小心点"，
而是理解到"一致性不能靠抽查"。这种反思质量在 7 年经验的人里也不常见。

## 最强与最弱

**最强的一条证据**

> 「现在回头看，那次的问题不是技术难，是我们把"数据一致"当成了可以抽查的东西。」

这句话值钱在**它是结论，不是描述**。绝大多数人复盘只讲"发生了什么"，
他讲的是"我们从根子上错在哪"。**这是高级工程师该有的反思层级。**

**最弱的一条证据**

> 「JVM 这块处理过 Full GC 频繁的问题，当时加了 GC 日志分析，调过堆大小和一些参数，后来就好了。」

**每一个词都在躲。**「一些参数」「后来就好了」——没有数字、没有根因、没有自己的作用。
简历上写着"熟悉 JVM 调优"，实测是"参与过一次，是运维主导的"。
**这条如果被真正的面试官咬住，是能直接判掉的。**

## 最该补的一件事

**补"失败路径"的思考习惯。**

你所有答得好的地方，都是**正常路径**：怎么并行、怎么拆、怎么迁移、怎么优化。
而所有卡住的地方，都是**异常路径**：

- 均值 840ms → P99 2.4s，**多出来的 1.5 秒你没想过**
- Lua 预扣成功 → 异步落库失败，**这笔账谁来平，你没想过**
- Redis 整个挂掉 → **你直接说"没仔细想过"**

**这不是知识缺口，是思维习惯。** 你不缺"Redis 挂了怎么办"的知识，
你缺的是**在设计的时候主动问自己"这一步失败了会怎样"**。

具体怎么练：下次写完一个方案，强制自己列三行——

```
如果这一步失败 → 系统处于什么状态 → 谁来修、什么时候修
```

拿你自己那个 Lua 预扣的方案练一遍，你会发现第二行和第三行是空的。
**那就是高级和中级之间的那道线。**

## 面试官备注（不给候选人看）

**这场面试官自身出了三个问题，已另附分析：**

1. **死磕同一话题 5 轮** —— 违反了 SOP「连续两次追问都答不上 → 记录边界，立刻换话题」
2. **漏掉了 JVM 那段典型的含糊回答** —— 违反「含糊必追问」（而它当时正困在别的话题上）
3. **一次假设式提问递了答案** —— 「是不是某个下游的尾延迟特别高？」接近「替候选人组织语言」

第 1 条和第 2 条其实是**同一个根因的两面**：精力被一个话题占住，
就没有余力去接别的话题。详见 `interviewer-issues.md`。
